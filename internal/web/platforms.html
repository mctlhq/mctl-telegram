For agent platforms

Connect your users to Telegram

This page is for agent platforms and MCP gateways that connect many users to {{.MCPURL}}. It covers how a client is admitted, what it may do, the limits it runs under, and how access ends. The limits and the CIMD status below are read from this deployment's running configuration.

Who this is for

A platform that lets its own users bring a Telegram account into an AI agent: one OAuth client on your side, one Telegram sign-in per user, each user's access confined to their own account. Individual users connecting Claude or ChatGPT need none of this page; the landing page and /docs cover them.

Admitting your client

A platform's host is approved by the operator once. After that, every one of its users connects without further setup on either side. There are two ways in:

Client ID Metadata Document (preferred)

  • Your client_id is an https URL on your own domain, and your redirect URIs come from the JSON document served there. You change callbacks by editing your document, not by asking us.
  • The document must name its own URL as client_id, carry no client_secret, list 1 to 20 https redirect_uris, and use token_endpoint_auth_method none or private_key_jwt (RS256 or ES256, with jwks_uri on the same host).
  • Fetches are bounded: 64 KiB body, 10-second timeout, and Cache-Control honored between 30 seconds and 24 hours. A document that cannot be fetched gives a retryable server_error; a CIMD client is never silently downgraded to DCR.
  • For private_key_jwt, the assertion's aud is the issuer {{.AuthServer}} or {{.AuthServer}}/oauth/token, lifetime at most 5 minutes, jti single-use.
On this deployment: {{if .CIMDAccept}}CIMD is accepted for approved hosts.{{else}}CIMD is not enabled.{{end}} {{if .CIMDAdvertise}}Discovery advertises it (client_id_metadata_document_supported).{{else}}Discovery does not advertise it yet, so a client that checks client_id_metadata_document_supported before using a URL client_id will register with DCR instead.{{end}}

Dynamic Client Registration

  • POST /oauth/register (RFC 7591) with redirect URIs on an approved host. Redirects are https, or http on loopback only; custom URL schemes are refused.
  • Registration is limited to {{.RegisterRatePerMin}} attempts per minute per source IP. A registration is kept for up to 24 hours, and the oldest ones are dropped sooner once the server reaches its cap on dynamic registrations, so register when a user connects rather than once at install.

To have a host approved, write to support@mctl.ai with the host, whether you use CIMD or DCR, and your expected number of users.

Scopes and consent

ScopeGrants
telegram:dialogs:readList chats (list_dialogs)
telegram:messages:readRead, search and fetch media (get_messages, get_unread_messages, search_messages, prepare_get_media, get_media)
telegram:messages:sendSend messages and media, edit, delete, forward and react, and the two-step draft_reply/send_reply on core-reply connections, all subject to the user's own consent below
telegram:messages:pinPin messages, through a confirmation step
account:manageThe user's own account: send consent, notifications, Local Bridge devices, disconnecting and deleting the account
  • Always name your scopes. A request that names scopes gets only those the user is entitled to; a request that omits scope gets the user's full entitled set, including send, pin and account:manage. Read the scope in the token response rather than assuming you got what you asked for. Administrative scopes cannot be requested.
  • The tool list follows the grant. tools/list shows only the tools the token's scopes allow, and a call to any other tool is refused as an unknown tool, so a read-only connection never sees the send tools.
  • Every account starts read-only. A send succeeds only when the scope is granted, the user has turned sending on themselves (by choosing Read + send when connecting, with set_send_consent{{if .ShowManage}} or on /telegram/connect/manage{{end}}), and the deployment allows sending{{if .AllowSend}} (it does on this deployment){{else}} (it does not on this deployment){{end}}. With the scope but without the user's consent, or on a deployment that does not allow sending, a send returns a preview with sent=false. Your platform cannot turn sending on for a user.
  • Every tool call lands in the user's hash-chained audit log, which they can read and verify. See /security.

Restricted tool profiles

On request, the operator can bind your client to a server-side tool profile. Profiles only restrict tools within the granted scopes and are enforced on every tool call (not just in tools/list):

  • core-readonly — list chats; read, check unread, and search within a single named chat, in pages of 20 (at most 50) and without inline media; plus the user's own identity, send status, and audit log.
  • core-reply — everything in core-readonly, plus a two-step reply flow: draft_reply previews the exact recipient and text without sending; send_reply requires the server-issued confirmation token and sends it at most once.

A binding matches your CIMD client_id or a redirect URI; ask at support@mctl.ai. Details: docs/design/core-profiles.md.

The tool surface is a contract

  • Every tool carries readOnlyHint and destructiveHint annotations. The full surface, schemas included, is committed as docs/tool-descriptors.json.
  • A release cannot add, remove or change a tool without an approved entry in the change feed at /docs/product-updates; CI enforces it.

Errors your client will see

docs/troubleshooting.md lists the error families clients actually hit, with the fix for each: expired access tokens, a revoked Telegram session (AUTH_KEY_UNREGISTERED), Telegram flood limits, redirect URI refusals and transient Telegram failures.

Revocation and offboarding

  • Your client revokes a user's grant with POST /oauth/revoke, which ends that refresh-token family. Access tokens already issued expire on their own lifetime ({{.AccessTTL}}).
  • {{if .ShowManage}}A user can disconnect their Telegram session on /telegram/connect/manage. {{end}}Disconnecting through a client (disconnect_telegram_account, POST /api/account/disconnect) and deleting the account (delete_telegram_account, DELETE /api/account) need account:manage, so request it if users should be able to leave from inside your platform.
  • Deleting an account revokes, in the same transaction as the delete, every client's refresh tokens for that user, every worker token issued for the user's Telegram ID, and every Local Bridge device with its credential. Worker and device credentials stop authenticating within 15 seconds, the revocation cache's refresh interval. Disconnecting ends the Telegram session but keeps the OAuth grant, so the user can reconnect without adding the connector again.
  • When a user removes your connector, the server learns of it only if your client calls /oauth/revoke; otherwise the grant stays valid until the refresh token expires or is revoked.
  • If an approved CIMD host is removed, its users' refreshes stop at the next token request.

Bring your own session: Local Bridge

For users or companies that will not leave a Telegram session on a hosted server, Local Bridge keeps it on the user's machine. The user installs mctl-telegram-local, signs in to Telegram locally and activates the device in a browser; your platform keeps the same endpoint and the same OAuth client. The server then relays MCP calls to that machine and sees the payloads in transit, so it is not end-to-end encryption. Local Bridge is in beta: the daemon must be running, and editing, deleting, forwarding, searching, reactions and the draft_reply/send_reply pair are not yet available in this mode.
